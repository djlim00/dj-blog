# 1. 컨슈머

![[Pasted image 20260710193523.png]]

- 프로듀서가 전송한 데이터는 카프카 브로커에 적재..
	- 컨슈머는 적재된 데이터를 사용하기 위해, 브로커에서 데ㅔ이터를 가져와서 필요한 처리를 한다.
	- ex) 마케팅 문자를 고객에게 보내는 기능 -> 브로커에서 고객 데이터를 가져와서 문자발송 처리

#### 컨슈머 내부 구조

![[Pasted image 20260710193639.png]]

- Fetcher
	- 리더 파티션으로부터 레코드들을 미리 가져와서 대기
- poll()
	- Fetcher.에 있는 레코드들들을 리턴하는 레코드
- ConsumerRecords
	- 처리하고자 하는 레코드들의 모음. 오프셋이 포함되어 있음

# 2. 컨슈머 그룹

![[Pasted image 20260710193754.png]]

- 컨슈머 그룹 : <mark class="hltr-yellow">컨슈머를 각 컨슈머 그룹으로부터 격리된 환경에서 안정하게 운영할 수 있게 해줌</mark>

- 컨슈머 그룹으로 묶인 컨슈머들은 토픽의 1개 이상 파티션들에 할당되어 데이터를 가져갈 수 있다.
	- 1개의 파티션은 최대 1개의 컨슈머에 할당 가능
	- <mark style="background:#b1ffff">컨슈머가 많으면 많을 수록, 파티션이 많은게 좋다!</mark>

#### 컨슈머 그룹의 컨슈머가 파티션 개수보다 많은 경우

![[Pasted image 20260710194356.png]]

- 노는 컨슈머가 생김
- 불필요한 스레드

#### 컨슈머 그룹을 활용해야하는 이유

![[Pasted image 20260710194421.png]]

- 운영 서버의 CPU, 메모리 정보를 수집하는 데이터 파이프라인을 구축한다고 가정하자.
	- 실시간 리소스를 시간순으로 확인 -> 엘라스틱서치
	- 대용량 적재 -> 하둡
	- <mark class="hltr-yellow">만약 카프카가 아니면, 서버에서 실행되는 리소스 수집 및 전송 에이전트는 수집한 데이터를 동기적으로 적재 요청을 해야함 -> 이때 엘서나 하둡 둘 중 하나라도 문제가 생기면 적재에 문제가 생길 수 있음.</mark>


![[Pasted image 20260710194615.png]]

- 카프카는 이런 파이프 라인 문제를 유연하게 대응하기 위해서 각기 다른 저장소에 저장되는 컨슈머를 다른 컨슈머 그룹으로 묶음 -> 저장소의 장애로부터 격리된다.
	- 그냥 한쪽에 문제 생겨도 진행
	- 문제해결되면 그쪽은 offset값 보고 진행

### 2. 수동 커밋 컨슈머 애플리케이션

#### 1. 동기 오프셋 커밋 컨슈머
```java hl:27
public class ConsumerWithSyncOffsetCommit {  
    private final static Logger logger = LoggerFactory.getLogger(ConsumerWithSyncOffsetCommit.class);  
    private final static String TOPIC_NAME = "test";  
    private final static String BOOTSTRAP_SERVERS = "my-kafka:9092";  
    private final static String GROUP_ID = "test-group";  
  
    public static void main(String[] args) {  
        Properties configs = new Properties();  
        configs.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);  
        configs.put(ConsumerConfig.GROUP_ID_CONFIG, GROUP_ID);  
        configs.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());  
        configs.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());  
        configs.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);  
  
        KafkaConsumer<String, String> consumer = new KafkaConsumer<>(configs);  
        consumer.subscribe(Arrays.asList(TOPIC_NAME));  
  
        while (true) {  
            ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));  
            Map<TopicPartition, OffsetAndMetadata> currentOffset = new HashMap<>();  
  
            for (ConsumerRecord<String, String> record : records) {  
                logger.info("record:{}", record);  
                currentOffset.put(  
                        new TopicPartition(record.topic(), record.partition()),  
                        new OffsetAndMetadata(record.offset() + 1, null));  
                consumer.commitSync(currentOffset);  
            }  
        }  
    }  
}
```
- 레코드 단위로 가져오는 것을 볼 수 있다
- comsuner.commitSycn() - 이 메서드로 동기 커밋을 명시적으로 수행할 수 있음.
	- commitSync()는 poll() 메서드 받은 가장 마지막  레코드의 오프셋을 기준으로 커밋
	- <mark class="hltr-yellow">동기 -> poll() 메서드로 받은 모든 레코드의 처리가 끝난 이후 commitSync() 메서드를 호출해야한다.</mark>

#### 2. 비동기 오프셋 커밋 컨슈머
```java hl:23
public class ConsumerWithASyncCommit {  
    private final static Logger logger = LoggerFactory.getLogger(ConsumerWithASyncCommit.class);  
    private final static String TOPIC_NAME = "test";  
    private final static String BOOTSTRAP_SERVERS = "my-kafka:9092";  
    private final static String GROUP_ID = "test-group";  
  
    public static void main(String[] args) {  
        Properties configs = new Properties();  
        configs.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);  
        configs.put(ConsumerConfig.GROUP_ID_CONFIG, GROUP_ID);  
        configs.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());  
        configs.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());  
        configs.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);  
  
        KafkaConsumer<String, String> consumer = new KafkaConsumer<>(configs);  
        consumer.subscribe(Arrays.asList(TOPIC_NAME));  
  
        while (true) {  
            ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));  
            for (ConsumerRecord<String, String> record : records) {  
                logger.info("record:{}", record);  
            }  
            consumer.commitAsync(new OffsetCommitCallback() {  
                public void onComplete(Map<TopicPartition, OffsetAndMetadata> offsets, Exception e) {  
                    if (e != null)  
                        System.err.println("Commit failed");  
                    else  
                        System.out.println("Commit succeeded");  
                    if (e != null)  
                        logger.error("Commit failed for offsets {}", offsets, e);  
                }  
            });  
        }  
    }  
}
```
- <mark class="hltr-yellow">동기 방법과 다르게 응답을 기다리는 동안 데이터를 처리할 수 있음 -> 더 많은 데이터 처리 가능</mark>


### 3. 리밸런스 리스너를 가진 컨슈머

```java hl:4,9
public class RebalanceListener implements ConsumerRebalanceListener {  
    private final static Logger logger = LoggerFactory.getLogger(RebalanceListener.class);  
  
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {  
        logger.warn("Partitions are assigned : " + partitions.toString());  
  
    }  
  
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {  
        logger.warn("Partitions are revoked : " + partitions.toString());  
    }  
}
```

- ComsumerRebalanceListener 인터페이스를 구현하면 된다!
	- onPartitionsAssigned() : 리밸런스가 끝난 후에 파티션이 할당 완료되면 호출되는 메서드
	- onPartitionsRevoked() : 리밸런스가 시작되기 직전에 호출되는 메서드. 마지막으로 처리한 레코드를 기준으로 커밋하기 위해 -> 이 함수에서 커밋을 구현하면 된다.
