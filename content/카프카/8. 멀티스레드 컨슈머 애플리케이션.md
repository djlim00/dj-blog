# 1. 멀티스레드 컨슈머

![[Pasted image 20260720112022.png]]

- 처리량을 늘리기 -> 파티션과 컨슈머를 늘린다.
	- (파티션 개수 == 컨슈머 개수)가 이상적
- 파티션의 개수가 n개 라면, 동일 컨슈머 그룹으로 묶인 컨슈머 스레드를 최대 n개 운영할 수 있음.
	- 그래서 n개의 스레드를 가진 1개의 프로세스를 운영하거나
	- 1개의 스레드를 가진 프로세스를 n개 운영하는 방법도 있다. (그림 참고)

# 컨슈머 랙

![[Pasted image 20260720112414.png]]

- <mark class="hltr-yellow">컨슈머 랙 = "파티션의 최신 offset과 컨슈머 offset 사이의 차이"</mark>
	- 프로듀서는 새로운 데이터를 파티션에 저장하고 -> 컨슈머는 자신이 처리할 수 있는 <u>만큼만</u> 가져간다.
- 컨슈머 랙은 컨슈머가 정상 동작하는지 확인할 수 있기 때문에 무조건 모니터링 해야하는 지표임.

#### ex) 컨슈머 랙 3개

![[Pasted image 20260720112707.png|452]]

- 위의 예시는 1개의 토픽에 3개의 파티션이 있음.
- 1개의 파티션이 해당 토픽을 구독 -> 컨슈머 랙은 총 3개가 된다.(파티션이 3개니까)



## 프로듀서와 컨슈머의 데이터 처리량

![[Pasted image 20260720112610.png]]

- 프로듀서가 컨슈머의 처리량 보다 데이터를 많이 보내면 늘어난다.
	- 0이 되면 지연이 없는 것

#### 컨슈머 랙이 중요한 이유
1. 카프카를 통한 데이터 파이프라인을 운영하는 핵심 지표
2. 컨슈머 장애 확인, 파티션 개수 정하는데 참고

ex) 추석이나 설날 같이 네비게이션 이용량이 늘어나면 -> 데이터 처리량이 늘어남.
- 이렇게 되면 컨슈머 랙이 발생할 수 있음.
- 일시적으로 파티션 개수와 컨슈머 개수를 늘려서 병렬처리량을 늘린다.
