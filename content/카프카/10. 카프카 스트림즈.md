# 1. 카프카 스트림즈
![[Pasted image 20260721111759.png]]

- <mark class="hltr-yellow">카프카 스트림즈 : 토픽에 적재된 데이터를 실시간으로 변환해서 다른 토픽에 적재하는 라이브러리</mark>
	- 자바 라이브러리 -> 자바 기반 스트림즈 애플리케이션은 카프카 클러스터와 완벽하게 호환
	- (스트림즈 애플리케이션 || 카프카 브로커)에 장애가 발생해도, exactly once할 수 있도록 장애 허요6ㅇ 시스템을 가지고 있음 -> <mark class="hltr-yellow">데이터 안정성이 매우 뛰어남</mark>
- 카프카 클러스터를 운영하면서 실시간 스트림 처리를 해야함 -> 카프카 스트림즈 애플리케이션을 사용하자!


### 프로듀서와 컨슈머를 조합하지 않고 스트림즈를 사용해야하는 이유

- 데이터 처리에 있어 필요한 다양한 기능 제공 -> 스트림즈DSL
	- 프로세서 API를 사용하여 기능을 확장할 수 있음
- 컨슈머와 프로듀서를 조합해서 스트림즈의 기능을 만들수는 있으나.... -> <mark style="background:#b1ffff">스트림즈 라이브러리가 제공하는 exactly once, fault tolerant system 등의 특징을 완벽하게 구현하기는 어렵다!</mark>

- 하지만 뭐 스트림즈가 제공하지 않는 기능은 만들어서 써야지
	- ex) 소스 토픽(사용하는 토픽)과 싱크 토픽(저장하는 토픽)의 카프카 클러스터가 서로 다른 경우는 스트림즈가 지원되지 않음 -> 컨슈머/프로듀서 조합으로 직접 클러스터를 지정하는 방법으로 개발


### 스트림즈 내부 구조

![[Pasted image 20260721112553.png]]

- 스트림즈 애플리케이션은 내부적으로 스레드를 1개 이상 생성할 수 있음
- 스레드는 1개 이상의 태스크를 가짐
	- **태스크** : 스트림즈 애플리케이션을 실행하면 생기는 데이터 처리 최소 단위
	- 3개 파티션 토픽 -> 스트림즈 애플리케이션 -> 3개 태스크
- 컨슈머 병렬처리를 위해 컨슈머 그룹으로 이루어진 컨슈머 스레드를 여러개 실행하는 것과 비슷하다.

#### 프로세서와 스트림
![[Pasted image 20260721112842.png]]

- **프로세서** : 카프카 스트림의 토폴로지를 이루는 **노드**
- **스트림** : 노드 **간선**
- **소스 프로세서** : 데이터를 처리하기 위한 최초 선언 노드(root node), 하나 이상의 토픽에서 데이터를 가져옴
- **스트림 프로세서** : 다른 프로세서가 반환한 데이터를 처리 -> 변환, 분기처리 같은 로직
- **싱크 프로세서** : 데이터를 특정 카프카 토픽으로 저장하는 역할 -> 스트림즈로 처리된 데이터의 최종 종착지


### 스트림즈DSL과 프로세서API

- 이 둘은 카프카 스트림즈에서 컨슈머/프로듀서 코드 작성을 할 때 다루는 방식 두가지를 말한다
	- 스트림즈DSL이 고수준(추상화 많이 되어 있음), 프로세서API가 저수준

- **스트림즈DSL** : 스트림 프로레싱에 쓰일만한 다양한 기능을 가진 API (변환로직 구현 쉬움)
- 만약 스트림즈DSL로 어려우면 프로세서API로 구현할 수 있음

# 2. 스트림즈DSL

## 1. KStream

![[Pasted image 20260721114136.png|425]]

- 레코드의 흐름을 표현한 것 (메시지 키 / 메시지 값)
- KStream으로 데이터를 조회하면 토픽에 존재하는 모든 레코드가 출력된다.

- <mark class="hltr-yellow">컨슈머로 토픽을 구독하는 것과 동일한 선상임.</mark>

## 2. KTable

![[Pasted image 20260721114614.png|400]]

- <mark class="hltr-yellow">KStream과의 핵심 차이는 **같은 키로 새 레코드가 왔을 때 "추가"로 보느냐 "덮어쓰기"로 보느냐**임.</mark>
- KStream과 다르게 메시지 키를 기준으로 묶어서 사용.
	- 유니크한 메시지 키를 기준으로 가장 최신의 데이터를 사용.


## 3. 코파티셔닝

![[Pasted image 20260721115146.png|392]]

- KStream이랑 KTable을 조인한다고 하면, **반드시 코파티셔닝이 되어 있어야함**
- **코파티셔닝** : <mark class="hltr-yellow">조인을 하는 2개 데이터의 파티션 개수가 동일하고 파티셔닝 전략을 동일하게 맞추는 작업.</mark> 


## 4. GlobalKTable

![[Pasted image 20260721115359.png|430]]

- 코파티셔닝을 보장하기 위해서 사용된다(조인을 하려고)
- KTable을 GlobalKTable로 선언하면 KStream이랑 코파티셔닝이 안되어 있어도 가능하다
	- KTable과 다르게 GlobalKTable로 정의된 데이터는 스트림즈 애플리케이션의 모든 태스크에 동일하게 공유되어 사용된다.
