## Prologue
- 카프카의 프로듀서는 뭘까?


# 1. 프로듀서

- 프로듀서는 리더 파티션과 직접 통신한다.
- 프로듀서는 카프카 브로커로 데이터를 전송할 때, 내부적으로 파티셔너, 배치 생성 단계를 거침.

#### 프로듀서 내부 구조
![[Pasted image 20260708221743.png]]

- ProducerRecord : 프로듀서에서 생성하는 레코드. 오프셋은 없음
- send() : 레코드를 전송 요청하는 메소드
- Partitioner : 해당 레코드를 어느 파티션에 전송할지 지정하는 파티셔너. 기본값으로는 DefaultPartitioner
- Accumulator : 배치로 묶어 전송할 데이터를 모으는 버퍼

___

# 2. 프로듀서 파티셔너

아래의 두가지 파티셔너를 제공한다. 현재는 UniformSticky 방식이 Default
1. UniformStickyPartitioner
2. RoundRobinPartitioner

#### 메시지 키가 있는 경우
- 두 방식 전부 메시지 키가 있을 때는 메시지 키의 해시값과 파티션을 매칭해서 전송
- 동일한 메시키 키 -> 동일한 파티션
- 만약 파티션 개수가 바뀌면 매칭이 깨짐

#### 메시지 키가 없을 때
1. RoundRobin
	- 레코드가 들어오는 대로 파티션을 순회하면서 전송
	- 전송 성능이 낮음(배치로 묶이지가 않음)

2. UniformSticky
	- Accumulator에서 배치로 묶일 때까지 기다렸다가 전송
	- 결국 파티션을 순회 -> 모든 파티션에 분배
	- RR 보다는 향상된 성능

> Partitioner 인터페이스가 있어서 커스텀 파티셔너를 만들 수도 있다.

___

# 3. ISR (In-Sync-Replicas)와 acks 옵션

- ISR은 리더 파티션과 팔로워 파티션이 모두 싱크가 된 상태
	- 즉 리더 파티션의 오프셋이 팔로워 파티션에 전부 존재해야함
- 복제에는 시간이 걸리기 때문에, 나온 용어
- 프로듀서가 특정 파티션에 데이터를 저장하는 작업 -> 리더 파티션을 통해서 한다.
	- 만약 리더 파티션에 샐운 레코드가 추가되서 오프셋이 증가하면 -> 팔로워 파티션이 위치한 브로커는 리더 파션의 데이터를 복제
	- 리더 적재 <mark class="hltr-yellow">이후</mark> 팔로워 파티션에 복제하는 시간차가 발생하기 때문에 파티션 간의 오프셋 차이가 발생


- acks 옵션은 0, 1, all(또는 -1)
- 얼마나 신뢰성 높게 저장할지 지정 가능
- <mark class="hltr-yellow">acks옵션에 따른 카프 동작 방식을 상세히 알고 설정해야함</mark>


### 안정적인 데이터 운영을 위한 복제 개수 2 이상인 경우의 acks별 동작 방식

### acks=0
- 0은 리더 파티션이 방금 받은 데이터의 오프셋 값에 대한 응답값을 받지 않음 -> 훨씬 빨라짐
- 데이터 유실이 발생해도 속도가 중요한 경우

### acks=1
- 1은 0의 반대 경우이다.
- 만약 리더에 적재되지 않았다면, 리더 파티션에 적재될 때까지 재시도할 수 있음.
- 이래도 데이터 유실 가능
	- 만약 리더의 데이터를 팔로워가 아직 복제(동기화) 안했는데, 리더 파티션의 브로커가 장애나는 경우

### acks=-1 (all)
- 0과 1의 경우를 전부 만족한 경우
- 속도가 느림
- 이런 경우는 replicas 값이 데이터의 안정성의 최후의 조건이 된다.(5개면 3개가 죽어도 괜찮지만, 3개면 3개가 죽으면 안됨)
