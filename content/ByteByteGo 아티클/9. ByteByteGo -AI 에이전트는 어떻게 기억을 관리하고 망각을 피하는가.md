# 도입

- 아무리 정교한 AI 에이전트를 써도, **매번 메시지는 완전한 백지 상태에서 시작합니다.**

- 모델 자체는 눈 앞에 두인 텍스트만 볼 수 있고, 이전 대화의 기록은 모델을 알 수 없죠.
- 그렇지만 저희가 Claude나 ChatGPT를 대화할 때는 연속성을 느낄 수 있습니다!
	- <mark class="hltr-yellow">이건 주변 플랫폼이 적절한 맥락을 다시 집어넣어 주면서, 해당 모델을 "대신해서" 만든 것 입니다.</mark>


이 글에서는 **그 아키텍처가 왜 존재해야하는지, 그리고 그 결과의 Trade-off가 뒤따르는지** 알아봅시다.

___

# 1. 무상태성 (Statelessness)
![[01-amnesiac-model.svg|717]]

- **LLM 호출은 단순한 패턴을 따름**
	- 시스템 프롬프트를 보낸다 -> 모델이 응답을 반환

이후 다음 요청을 완전히 새 백지 상태에서 시작합니다. 즉 무상태성을 가집니다.

- 따라서 "클로드는 어제의 대화를 기억한다"라고 하면 그건 AI모델의 특성이 아니라, 해당 제품의 속성
- <mark class="hltr-yellow">플랫폼</mark>이 모델을 대신해서 대화를 기록하고, 정확한 시점에 그걸 프롬프트에 다시 넣어줌

> 즉 지능은 모델 안에, 기억은 모델을 둘러싼 시스템(플랫폼)에 있다!

___

# 2. 컨텍스트 (Context) 
![[02-context-window-anatomy.svg|717]]


- 모든 API 호출은 <mark class="hltr-yellow">컨텍스트 윈도우(모델이 한 번에 읽을 수 있는 텍스트 영역)</mark>이 있음
	- 시스템 프롬프트, 사용자의 현재 메시지, 그 외 컨텍스트

#### 모든 대화 기록을 매 호출에 컨텍스트로 넣는다?

- 처음에는 잘 동작하지만 아래의 문제가 발생합니다.

1. **비용**
	- 연속성 유지를 위한 토큰 증가

2. **지연시간**
	- 컨텍스트가 긴 만큼 처리시간 증가

3. **모델의 주의력 저하**
	- 중간의 정보는 소실된다!


> 그렇다면 어떤 정보가 언제 컨텍스트 윈도우에 들어가야하는지 결정하는 아키텍처가 필요함

___

# 3. 계층 (Hierarachy)
![[04-memory-hierarchy.svg|717]]
- 실제 프로덕션 시스템은 메모리를 계층(tier)로 조직함
	- 각 계층은 "접근 속도", "총 용량", "토큰당 비용"을 서로 다른 방식으로 Trade-off함
- <mark class="hltr-yellow">맨 위에 컨텍스트 윈도우 가 있고, 그 아래로 점점 느리고, 크고, 저렴한 저장소가 있음</mark>

1. **컨텍스트 윈도우**
	- 빠르고, 용량이 꽉 참, 규모가 커지면 토큰당 비용이 크게 부담

2. **세션 메모리**
	- 아직 요약되거나 밀려나지 않은 최근 활동

3. **장기 저장소**
	- 세션을 넘어 지속되는 사실
	- 임베딩

4. **콜드 아카이브**
	- 감사 목적이나 미래 참조를 위해 저장
	- 거의 접근하지 않음

에이전트는 이 계층을 오르내리면서 정보를 봅니다. 관련성이 생기면 꺼내서 컨텍스트 윈도우로 승격하고, 반대로 세션이 끝나면 장기 저장소로 끌어내립니다.

ChatGPT의 메모리는 단순한 형태를 씁니다. 최근 대화 요약+저장된 사용자 사실은 프롬프트 앞에 붙고, 현재 세션은 작업 계층.

> 핵심은 "정고한 검색이 아닌, 애초에 무엇을 장기 메모리로 승격시킬 것인가"
> 그렇다면 어떤 종류의 메모리를 저장하고 있을까?

___

# 4. 데이터 유형 (Type)
![[05-four-memory-types.svg|717]]

1. **작업 메모리 (Working Memory)**
	- 현재 작업을 위한 라이브 컨텍스트 윈도우
	- ex) 현재 디버깅을 하고 있으면, 최근 함수 코드+최근 메시지
	- 작업이 끝나면 작업 메모리를 비워짐

2. **일화적 메모리 (Episodic Memory)**
	- 특정 과거 대화의 기록
	- ex) "어제, 신입 개발자의 온보딩에 대해 물었고, 우리는 체크 리스트를 만들었다"
	- 사건+맥락

3. **의미 메모리(Semantic Memory)**
	- 특정 대화가 아닌 사실과 지식
	- ex) "사용자의 팀은 Github Action로 CI를 한다"

4. **절차 메모리 (Procedural Memory)**
	- 학습된 일 처리 방식
	- 과거의 특정 작업을 어떻게 했는지를 저장

이런 데이터들은 관련성이 생기면 컨텍스트 윈도우로 승격될 수 있습니다.
대부분 위와 같은 데이터 유형 중에 최소 세가지는 구현합니다.
ex) 코딩 에이전트는 절차 메모리를 더 중시함
ex) 고객 지원 에이전트는 일화적 메모리와 의미 메모를 중시

> 그렇다면 매 턴 마다 어떤 데이터를 꺼낼지 어떻게 결정할까?

___

# 5. 검색 (Retrieval)

![[06-read-write-loop.svg|717]]

- DB 혹은 벡터 저장소에 저장한다 -> 쉬움
- <mark class="hltr-yellow">그렇다면 매 턴 마다 어떤 것이 중요한지 어떻게 검색해야할까?</mark>
	- 관련성 판단(메시지 마다 다름)
	- ex) 프로젝트를 할 때는 파이썬 선호가 중요, 하지만 피자 레시피에서는 중요하지 않음!

위 그림을 보면 어떻게 검색을 하는건지 알 수 있습니다!

1. 메시지 보냄
2. 키워드 검색, 의미적 유사도, 최신성 신호 조합으로 **메모리 계층에서 관련 항목을 꺼냄**
3. 컨텍스트 윈도우를 조립
4. 응답
5. 다시 응답 내용을 메모리에 저장(시간이 지날수록 중요도 Down - decay score)

**검색은 에이전트의 성능 좌우하는 중요한 부분입니다.**
-> 응답을 위해서 의존해야하는 데이터의 경계를 정해주기 때문에

즉 프로덕션의 엉뚱한 대답이 나오는 경우는 대부분 검색 실패입니다.

___

# 6. 트레이드 오프(Tradeoffs)

##### 1. 최신성 vs 관련성
- 가장 최근의 항목이 중요한가 vs 가장 의미적으로 비슷한게 중요한가
- 이걸 잘 섞는건 여전히 진행 중인 문제임

##### 2. 요약 vs 충실도
- 요약 -> 토큰 절약 -> 세부정보 손실

##### 3. 낡음(Staleness)
- 과거의 정답이 지금은 아닐 수 있습니다.
- 예전의 답변을 자신있게 낼 수 있음..

##### 4. 메모리 오염
- 장기 메모리 -> 장기적인 공격 표면
- 과거의 악성적인 컨텍스트가 매 검색에 악영향을 끼칠 수 있음
- 지속성이 문제가 될 수 있다는 말

___

# 7. 결론

1. 모델은 무상태다.

2. 컨텍스트 윈도우가 모델이 인식하는 범위이다.

3. 실제 시스템은 메모리를 계층 구조로 조직한다.

4. 정보의 종류에 따라 다른 종류의 메모리가 필요하다.

5. 검색이 가장 핵심적인 부분이다.
