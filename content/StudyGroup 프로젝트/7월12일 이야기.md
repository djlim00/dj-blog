#### 1. Entity에  Ref vs Primitive 차이

- Entity에서 참조타입을 쓰는 이유는 null값이 들어갈 수 있기 때문에 DB에서의 null 처리를 하기가 편해서로 알고 있음.

1. 데이터의 복잡성
- 필드가 단순한 값을 가지는 경우 → **원시 타입**이 더욱 간단&효율적

2. 객체의 관계
- 필드가 다른 객체와의 관계(일대다, 다대다 등)를 표현하는 경우 → **참조 타입**

 3. **Null 값 처리**
- 참조 타입은 null 값을 허용할 수 있으므로, 필드가 null 값을 가질 수 있는 경우 → **참조 타입** 사용이 더 유용

 4. 특정 라이브러리 또는 프레임워크의 요구 사항
- 데이터베이스 매핑을 위한 ORM 프레임워크인 Hibernate나 JPA와 같은 경우에는 일반적으로 참조 타입을 사용하는 것이 더 편리합니다. 이러한 라이브러리는 관련된 객체를 로드하고 관리하는 기능을 제공하기 때문입니다.


#### 2. Void를 사용한이유

#### 3. 제너릭에서 < T >는 뭐고 왜 쓴걸까? 지우면 무슨 문제가 발생할까? 
- < T>는 이제 미리 타입을 지정하지 않고, 사용할 때 정해지는 타입을 의미.

- **타입 파라미터 선언**: 컴파일러에게 `T`가 미리 지정된 특정한 클래스가 아니라, 메서드가 호출될 때 동적으로 결정되는 타입(Type)임을 알려줍니다.
- **범위 지정**: 반환 타입이나 매개변수에서 `T`를 사용할 수 있게 합니다.

## 5. Logback

### Logback이란

- Java의 **로깅 프레임워크**입니다. Spring Boot의 기본 로깅 라이브러리입니다.
- "로그를 어디에, 어떤 형식으로, 어떤 조건에서 남길지"를 설정으로 결정합니다.

### 왜 필요한가

- 애플리케이션이 지금 무슨 일을 하고 있는지 알려면 로그가 필요합니다.
- 그런데 **로그를 실시간으로 WAS에서 직접 뽑아볼 수는 없습니다.**
    - 서버에 SSH로 들어가서 매번 확인하는 건 불가능합니다.
    - 인스턴스가 여러 대면 어디를 봐야 할지도 모릅니다.

> <mark class="hltr-yellow">Logback은 로그를 "적재해둘 수 있는 통로"를 만들어줍니다.</mark>  
> 남긴 로그를 나중에 수집·분석 도구가 가져갈 수 있게 하는 것이 핵심입니다.

---

### 1) 로그 레벨 (Level)

로그에는 심각도 등급이 있습니다.

```
TRACE < DEBUG < INFO < WARN < ERROR
```

- 설정한 레벨 **이상**만 출력됩니다.
- 개발 환경에서는 `DEBUG`, 운영에서는 `INFO`처럼 다르게 둡니다.
    - 운영에서 `DEBUG`를 켜면 로그가 폭발합니다.

---

### 2) 어펜더 (Appender)

**어펜더는 "로그를 어디에 쓸 것인가"를 정하는 출력 대상**입니다.

##### ConsoleAppender

- 콘솔(표준 출력)에 찍습니다.
- 로컬 개발할 때 IDE 터미널에서 보는 그것입니다.

##### FileAppender / RollingFileAppender

- **실제 배포 환경에서는 콘솔이 의미가 없습니다.** 아무도 안 보고 있으니까요.
- 그래서 **파일로 떨궈둡니다.**
- `RollingFileAppender`는 조건에 따라 파일을 새로 만듭니다.
    - **날짜별** — 하루가 지나면 `app-2026-07-12.log` 같은 새 파일 생성
    - **크기별** — 파일이 일정 용량을 넘으면 새 파일 생성
    - 오래된 파일은 자동 삭제 (보관 기간 설정)

> 파일 하나에 계속 쌓으면 몇 GB짜리 파일이 되어 열어볼 수도 없습니다. 그래서 쪼갭니다.

##### AsyncAppender

- 로그를 남기는 건 **I/O 작업**입니다. 느립니다.
- 이걸 동기적으로 하면 **비즈니스 로직이 로그를 기다립니다.**
- `AsyncAppender`는 로그를 큐에 넣고 **별도 스레드**가 처리하게 합니다.
    - 애플리케이션은 바로 다음 일을 합니다.

---

### 3) JSON 포맷

- 사람이 읽기 좋은 형태(`2026-07-12 00:41:04 INFO ...`)는 **기계가 파싱하기 어렵습니다.**
- 로그 수집 도구가 가져갈 거라면 **JSON으로 남기는 게 낫습니다.**

json

```json
{"timestamp":"2026-07-12T00:41:04","level":"ERROR","logger":"...","message":"...","traceId":"abc123"}
```

- 필드가 구조화되어 있으니 **검색·필터링·집계**가 쉽습니다.
- "지난 1시간 동안 traceId가 abc123인 ERROR만" 같은 질의가 가능해집니다.

---

### 4) 그 다음 — ELK

Logback이 파일을 떨궈두면, 그것을 가져가는 쪽이 있습니다.

|도구|역할|
|---|---|
|**Logstash** (또는 Filebeat)|로그 파일을 **수집**해서 전달|
|**Elasticsearch**|로그를 **저장·검색**|
|**Kibana**|로그를 **시각화**·조회|

> Logback은 "로그를 잘 남기는 것"까지가 역할입니다.  
> **수집·저장·시각화는 별도 도구의 몫**입니다. 역할이 분리되어 있습니다.

---

### 정리

|환경|어펜더|형식|
|---|---|---|
|로컬 개발|Console|사람이 읽기 좋게|
|운영 배포|RollingFile + Async|**JSON**|

1. Logback은 **로그를 남기는 도구**입니다. 분석 도구가 아닙니다.
2. 콘솔은 개발용, **운영에서는 파일**로 남깁니다.
3. 파일은 **날짜·크기별로 쪼갭니다** (Rolling).
4. 로그 I/O가 로직을 막지 않도록 **비동기(Async)** 로 씁니다.
5. 수집 도구가 파싱하기 쉽게 **JSON**으로 남깁니다.
6. 그 파일을 **ELK가 가져가서** 검색·시각화합니다.
