## 1. 왜 Lua인가

- Redis의 개별 명령어는 원자적입니다. `INCR` 하나는 중간에 끊기지 않습니다.
- **그런데 여러 명령어를 "하나의 단위"로 묶어야 한다면?**

선착순 정원 마감을 예로 들어보면,,
정원 10명인 스터디에 신청을 받는다고 하면, 로직은 이렇습니다.

1. 현재 인원을 읽는다 (`GET`)
2. 10명 미만인지 확인한다
3. 미만이면 1 증가시킨다 (`INCR`)

- 세 명령을 따로 보내면 **1번과 3번 사이에 남이 끼어들 수 있습니다.**

```
클라이언트 A: GET → 9명
클라이언트 B: GET → 9명       ← A가 INCR 하기 전에 끼어듦
클라이언트 A: INCR → 10명
클라이언트 B: INCR → 11명      ← 정원 초과!
```

- 이것이 <mark class="hltr-yellow">경쟁 조건(race condition)</mark>입니다.

##### MULTI/EXEC 트랜잭션으로는 안 되나?

- Redis에도 트랜잭션(`MULTI`/`EXEC`)이 있습니다. 여러 명령을 큐에 쌓았다가 한 번에 실행합니다.
- 하지만 **중간 결과를 보고 판단할 수 없습니다.**
    - 명령을 미리 다 적어서 보내고, 결과는 마지막에 한꺼번에 받습니다.
    - "GET 결과가 10 미만이면 INCR" 같은 조건문을 쓸 수 없습니다.

> Lua 스크립트만이 **중간 값을 읽고, 그 값으로 판단하고, 그 판단에 따라 다른 명령을 실행**하는 것을 원자적으로 할 수 있습니다.

---

## 2. Lua 스크립트란

- Redis는 **Lua 5.1 인터프리터를 서버 안에 내장**하고 있습니다.
- 클라이언트가 스크립트를 서버로 보내면, Redis가 그걸 실행합니다.

lua

```lua
-- claim-capacity.lua
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
local capacity = tonumber(ARGV[1])

if current < capacity then
    redis.call('INCR', KEYS[1])
    return 1        -- 신청 성공
else
    return 0        -- 정원 마감
end
```

- `KEYS[1]` — 스크립트가 다룰 키 (예: `studygroup:group:1:count`)
- `ARGV[1]` — 그 외 인자 (예: 정원 10)
- `redis.call(...)` — 스크립트 안에서 Redis 명령 실행

**Redis는 단일 스레드입니다.** 스크립트가 도는 동안 다른 명령은 아무것도 실행되지 않습니다. 그래서 위 세 단계가 통째로 원자적입니다.

---

## 3. 장점

##### 1. 원자성 (Atomicity)

- 스크립트 실행 중 **서버의 모든 활동이 차단**됩니다.
- 스크립트의 모든 효과는 "아직 일어나지 않았거나, 이미 다 일어났거나" 둘 중 하나입니다. 중간 상태가 남에게 보이지 않습니다.
- 경쟁 조건이 원천적으로 사라집니다.

##### 2. 네트워크 왕복 감소

- 스크립트가 **데이터가 있는 곳(서버)에서 실행**됩니다.
- GET → 판단 → INCR을 각각 보내면 왕복 2~3번. Lua면 **1번**입니다.

##### 3. 조건부 로직

- 앞서 말한 대로, MULTI/EXEC이 못 하는 "중간 값 기반 판단"이 가능합니다.
- 분산 락, 레이트 리미터, 잔액 확인 후 차감 등이 대표적입니다.

---

## 4. 단점

##### 1. Stop-The-World

- **Lua 실행은 Redis 인스턴스 전체를 멈춰 세우는 작업입니다.**
- 장점(원자성)의 원인이 그대로 단점이 됩니다. 스크립트가 오래 걸리면 **그동안 다른 모든 클라이언트가 대기**합니다.
- 그래서 <mark class="hltr-yellow">복잡한 연산이나 긴 스크립트를 Redis에 넣으면 안 됩니다.</mark>
- 실행이 설정된 임계치를 넘으면 "느린 스크립트"로 간주되고, 이걸 중단하는 유일한 방법은 `SCRIPT KILL`입니다.
    - 단, 데이터를 수정한 스크립트는 죽일 수 없습니다. (원자성이 깨지니까)

##### 2. 디버깅과 테스트가 어렵다

- Lua 코드는 읽기 어렵고 테스트하기 어렵습니다.
- IDE 지원, 타입 체크, 단위 테스트 모두 애플리케이션 코드보다 열악합니다.

##### 3. 스크립트가 영속화되지 않는다

- **이게 가장 놓치기 쉬운 부분입니다.**
- EVAL 스크립트는 이름이 붙지도, 버전이 매겨지지도, **디스크에 저장되지도 않습니다.**
- 서버 재시작이나 **레플리카로의 페일오버 후에는 스크립트를 다시 로드해야 합니다.**

> 실제로 Sentinel 페일오버 실습에서 이걸 만납니다.  
> master가 죽고 replica가 승격되면, 새 master에는 스크립트가 없습니다.  
> → `NOSCRIPT` 에러 → Spring의 `DefaultRedisScript`가 자동으로 `SCRIPT LOAD` 재실행

##### 4. 외부 세계에 접근할 수 없다

- HTTP 호출, 파일 접근 불가. 오직 Redis 안의 데이터만 다룹니다.

## 5. 언제 쓰지 말아야 하는가

|상황|대신 쓸 것|
|---|---|
|단일 명령으로 충분함|`INCR`, `GETSET` 등 원자적 명령어|
|스크립트가 50줄을 넘음|애플리케이션 코드로 로직 이동|
|외부 데이터가 필요함|Lua로 불가능|
|실행 시간이 예측 불가능|Redis를 블로킹하면 안 됨|

> 원자성이 **꼭 필요한** 짧은 로직에만 쓴다. 이게 원칙입니다.

---

## 6. EVAL vs EVALSHA

- `EVAL` — 매번 스크립트 전문을 서버로 보냄. 네트워크 낭비.
- `EVALSHA` — 스크립트를 한 번 `SCRIPT LOAD` 해두고, **SHA1 해시로만 호출**.

Spring의 `DefaultRedisScript`는 EVALSHA를 먼저 시도하고, `NOSCRIPT`가 나면 자동으로 다시 로드합니다. 페일오버 대응이 이미 들어 있는 셈입니다.

---

## 7. 결론

1. 개별 Redis 명령은 원자적이지만, **여러 명령을 묶으려면 Lua가 필요하다.**
2. MULTI/EXEC은 **중간 값으로 판단할 수 없다.** Lua만 가능하다.
3. 장점(원자성)의 대가는 **Stop-The-World**다. 스크립트는 짧아야 한다.
4. 스크립트는 **영속화되지 않는다.** 페일오버 후 재로드가 필요하다.
5. 원자성이 꼭 필요할 때만 쓴다. 아니면 애플리케이션 코드가 낫다.
