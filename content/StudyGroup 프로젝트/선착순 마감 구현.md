## Prologue  
- Redis Lua 스크립트로 선착순 정원 마감 구현  
- 동시성 검증과 놓치기 쉬운 것들  
  
  
이미 DB의 `SELECT FOR UPDATE`나 애플리케이션 락으로 동시성을 처리해보셨을 터인데,  
Redis로 선착순을 구현하면 어떤 점에서 좋은 걸까요?  
  
1. DB 락처럼 처리량이 급감하지 않음  
2. 서버가 여러 대여도 정원이 정확히 지켜짐  
3. 도메인 로직에서 저장소 기술을 모르게 격리할 수 있음  
  
이번 글은 100명이 정원 10명 모임에 **동시에** 신청하는 상황에서, 정확히 10명만 통과시키는 방법을 다룹니다.  
  
아래 코드는 전부 실제로 이번 프로젝트에 작성된 코드들입니다!

## Part 1. Redis Lua 스크립트로 선착순 구현  
  
### 왜 순진한 접근은 실패하나  
  
가장 먼저 떠오르는 코드는 이렇습니다.  
  
```java  
long current = countActiveMembers(groupId);   // DB SELECT

if (current >= capacity) throw new GroupFullException(...);

saveMembership(...);                          // DB INSERT
```  
  
문제는 **SELECT와 INSERT 사이에 다른 트랜잭션이 끼어들 수 있다는 것**입니다.  
100개 요청이 동시에 SELECT하면 전부 "아직 자리 남았음"이라고 판단해 100명이 다 저장됩니다.  
  
락으로 해결하는 방법도 있지만:  
  
- `SELECT FOR UPDATE` — DB 락 대기로 처리량 급감  
- 애플리케이션 락 — 서버가 여러 대면 무효 (인스턴스 A의 락을 B는 모름)  
- 분산 락 라이브러리 — 결국 Redis 원자 연산을 우회하는 셈  
  
### Redis가 원자성을 보장하는 이유  
  
**Redis는 명령 실행이 단일 스레드**입니다. Lua 스크립트를 보내면, 그 스크립트가 실행되는 동안 다른 명령이 끼어들 수 없어요. 즉 **스크립트 전체가 하나의 원자 실행 단위**가 됩니다.  
  
이 특성을 이용해서, "GET → 정원 미만이면 INCR, 아니면 실패"를 한 덩어리로 실행하는 스크립트를 만듭니다.  
  
### Lua 스크립트  
  
```lua hl:8-10 title:studygroup-infra/src/main/resources/redis-scripts/claim-capacity.lua
-- KEYS[1] = studygroup:group:{groupId}:count  
-- ARGV[1] = capacity  
  
local current = redis.call("GET", KEYS[1])  
current = current and tonumber(current) or 0  
  
local capacity = tonumber(ARGV[1])  
if current >= capacity then  
    return -1end  
  
return redis.call("INCR", KEYS[1])  
```  
  
- `GET`으로 현재 카운트 조회  
- 정원 이상이면 `-1` 반환 (FULL)  
- 미만이면 `INCR`로 원자적 +1 (CLAIMED)  
  
**GET과 INCR 사이에 다른 요청이 끼어들 수 없기 때문에**, 카운트는 절대 capacity를 초과할 수 없습니다.  
  
### 도메인은 Redis를 모르게 격리 (포트-어댑터)  
  
여기서 중요한 설계 포인트! 도메인 코드에 `RedisTemplate`이 들어가면 안 됩니다.  
도메인은 "자리 확보를 시도한다"라는 개념만 알아야 하고, 그게 Redis든 HashMap이든 몰라야 해요.  
  
그래서 도메인 모듈에는 **인터페이스만** 정의합니다.  
  
```java  
// studygroup-domain  
public interface CapacityCounter {  
  
    ClaimResult tryClaim(long groupId, int capacity);  
    void release(long groupId);  
    int currentCount(long groupId);}  
  
public enum ClaimResult { CLAIMED, FULL }  
```  
  
Redis 구현은 인프라 모듈에.  
  
```java hl:15-20  
// studygroup-infra
@Component
public class RedisCapacityCounter implements CapacityCounter {

    private final StringRedisTemplate redisTemplate;
    private final DefaultRedisScript<Long> claimScript;

    public RedisCapacityCounter(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
        this.claimScript = new DefaultRedisScript<>();
        this.claimScript.setLocation(new ClassPathResource("redis-scripts/claim-capacity.lua"));
        this.claimScript.setResultType(Long.class);
    }

    @Override
    public ClaimResult tryClaim(long groupId, int capacity) {
        Long result = redisTemplate.execute(
                claimScript,
                List.of("studygroup:group:" + groupId + ":count"),
                String.valueOf(capacity)
        );
        if (result == null || result < 0) {
            return ClaimResult.FULL;
        }
        return ClaimResult.CLAIMED;
    }

    // ...
}
```  
  
- 도메인은 `CapacityCounter` 인터페이스만 알고 있다  
- Spring이 `RedisCapacityCounter`를 자동으로 주입해준다  
- 나중에 저장소 기술을 바꾸고 싶다면 어댑터만 갈아끼우면 된다  
  
### 서비스에서 호출  
  
```java hl:9-13  
@Transactional
public Membership apply(Long studyGroupId, Long userId) {
    StudyGroup group = studyGroupRepository.findById(studyGroupId).orElseThrow(...);

    if (group.isHostedBy(userId)) {
        throw new CannotApplyToOwnGroupException();
    }
    membershipRepository.findByStudyGroupIdAndUserId(studyGroupId, userId)
            .ifPresent(existing -> { throw new AlreadyAppliedException(existing.getStatus()); });

    if (group.isFirstCome()) {
        ClaimResult result = capacityCounter.tryClaim(studyGroupId, group.getCapacity());
        if (result == ClaimResult.FULL) {
            throw new GroupFullException(studyGroupId);
        }
        return membershipRepository.save(Membership.applyAsApproved(studyGroupId, userId));
    }
    return membershipRepository.save(Membership.apply(studyGroupId, userId));
}
```  
  
- 이 서비스 코드에서 "Redis"라는 단어가 한 번도 안 나옵니다  
- `capacityCounter`가 Redis로 이야기하는지, HashMap으로 이야기하는지 도메인은 모른다  
- 단위 테스트에서 fake 구현으로 갈아끼우면 Redis 없이도 로직 검증 가능

## Part 2. 정말 되는지 증명하기  
  
말로만 "원자적이다" 라고 하면 안 되겠죠. **100명이 정원 10명 모임에 동시 신청하는 상황을 통합 테스트로 재현**합니다.  
  
### 통합 테스트  
  
```java hl:18-32  
@SpringBootTest
class MembershipConcurrencyTest {

    private static final int CAPACITY = 10;
    private static final int TOTAL_APPLICANTS = 100;

    @Test
    void 정원_10명_모임에_100명_동시_신청_10명만_승인() throws Exception {
        // given
        StudyGroup group = studyGroupRepository.save(StudyGroup.create(
                "선착순 테스트", "설명", CAPACITY, host.getId(), JoinMode.FIRST_COME
        ));
        redisTemplate.delete("studygroup:group:" + group.getId() + ":count");
        List<Long> applicantIds = /* 100명 사용자 생성 */;

        // when — 100명 동시 발사
        ExecutorService pool = Executors.newFixedThreadPool(50);
        CountDownLatch startGate = new CountDownLatch(1);
        AtomicInteger approvedCount = new AtomicInteger();
        AtomicInteger fullCount = new AtomicInteger();

        List<CompletableFuture<Void>> futures = applicantIds.stream()
                .map(uid -> CompletableFuture.runAsync(() -> {
                    try {
                        startGate.await();
                        membershipService.apply(group.getId(), uid);
                        approvedCount.incrementAndGet();
                    } catch (GroupFullException e) {
                        fullCount.incrementAndGet();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                }, pool))
                .toList();

        startGate.countDown();
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

        // then — 정확히 10명 승인, 90명 실패
        assertEquals(CAPACITY, approvedCount.get());
        assertEquals(TOTAL_APPLICANTS - CAPACITY, fullCount.get());

        // DB에도 정확히 10개
        List<Membership> approvedInDb = membershipRepository
                .findAllByStudyGroupIdAndStatusOrderByIdAsc(group.getId(), MembershipStatus.APPROVED);
        assertEquals(CAPACITY, approvedInDb.size());

        // Redis 카운트도 정확히 10
        String redisCount = redisTemplate.opsForValue()
                .get("studygroup:group:" + group.getId() + ":count");
        assertEquals(String.valueOf(CAPACITY), redisCount);
    }
}
```  
  
- `CountDownLatch`로 모든 스레드가 **동시에** 시작하도록 강제 (경합을 최대화)  
- 애플리케이션 카운트, DB 카운트, Redis 카운트 **세 곳 다** 검증  
- 3회 연속 실행해서 결과가 결정론적인지 확인  
  
### 결과  
  
| 실행 | APPROVED | FULL | DB APPROVED | Redis count |  
|---|---|---|---|---|  
| Run 1 | 10 | 90 | 10 | 10 |  
| Run 2 | 10 | 90 | 10 | 10 |  
| Run 3 | 10 | 90 | 10 | 10 |  
  
3회 연속 결정론적 통과. Redis Lua 스크립트가 100명 동시 상황에서 정확히 10명만 통과시킴을 코드로 증명했습니다.

## Part 3. 놓치기 쉬운 것들  
  
### 강퇴하면 자리 하나가 반환되어야 함  
  
선착순으로 참여한 사람이 강퇴당하면, 그 자리는 다시 비어야겠죠. 그래서 `MembershipService.kick`은 선착순 모드일 때 `capacityCounter.release(groupId)`를 호출해 카운트를 원자적 DECR 합니다.  
  
```java hl:5-7  
public Membership kick(Long membershipId, Long actorUserId) {
    Membership membership = requireHostAccess(membershipId, actorUserId);
    StudyGroup group = studyGroupRepository.findById(membership.getStudyGroupId()).orElseThrow(...);

    membership.kick();

    if (group.isFirstCome()) {
        capacityCounter.release(membership.getStudyGroupId());
    }
    return membership;
}  
```  
  
승인제 모드에서는 카운트 자체가 없으니 no-op으로 자연스럽게 넘어갑니다.  
  
### 앱 재시작해도 카운트가 살아있어야 함  
  
Docker Compose에 `--appendonly yes` (AOF 활성화)를 걸어 뒀습니다. 앱이나 Redis가 재시작해도 카운트가 디스크에서 복원됩니다.  
  
```yaml  
redis:  
  image: redis:7-alpine  command: ["redis-server", "--appendonly", "yes"]  
```  
  
이거 안 해두면 재배포마다 카운트가 0으로 리셋되어 정원 초과가 발생할 수 있어요.  
  
### tryClaim은 성공했는데 DB 저장이 실패하면?  
  
Redis 카운트는 이미 증가했는데 DB 저장이 실패하면, 카운트가 누수됩니다. 100명 유일 사용자 시나리오에서는 발생하지 않지만, 프로덕션 하드닝에서는 try-catch로 `release`를 호출해서 롤백해줘야 합니다.

## Epilogue  
  
Redis를 세션 저장소로만 알던 시각에서 벗어나면, **원자 연산으로 동시성 문제를 우아하게 푸는 도구**로 보이기 시작합니다.  
  
핵심은 두 가지였어요.  
  
1. Redis 명령 실행은 단일 스레드 → Lua 스크립트가 원자 실행 단위  
2. 도메인은 저장소 기술을 몰라야 함 → 포트-어댑터로 격리  
  
Redis 한 프로젝트에서 **세션 저장 → 원자 연산 → 랭킹**으로 확장해가는 시리즈로 이어질 예정입니다. 다음 편에서는 Sorted Set으로 출석률 랭킹을 만들어보겠습니다.
