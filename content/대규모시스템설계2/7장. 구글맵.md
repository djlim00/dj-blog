## 1. 지도 101

#### 측위 시스템
- 지구(구) 표면 상의 위치를 표현하는 체계
- 위경도 기반 측위 시스템

![[Pasted image 20260626111531.png|218]]

- 위도(lat) : 북/남
- 경도(lon) : 서/북 

#### 그럼 이 3차원의 구를 2차원 평면에 두는 것 -> 지도 투영법(도법)

- 하지만, 각각의 방법은 왜곡이 발생할 수 밖에 없음.
	- 구글 -> 웹 메르카토르 기법 

#### 지오코딩(Geocoding)
- 주소를 측위 시스템으로 ex) 성남시 분당구 판교로50 -> {36.xxx, 20.xx}
- 역 지오코딩 -> 위경도를 주소로

- 인터폴레이션을 이용해서 수행할 수 있음 ex) GIS(Geographic information System)

#### 지오해싱(Geohashing)
- 지도 위 특정 영역을 영문자와 숫자로 구성된 짧은 문자열에 대응시키는 인코딩 체계.
- 2차원의 평면 공간으로 표현된 지리적 영역 위의 격자를 더 작은 격자로 재귀적으로 분할
	- 격자 -> 정사각형 or 사각형
	- 재귀적으로 분할된 더 작은 격자 -> 0~3사이의 번호를 부여
>wydm6 → 강남역 근처 
>wydm7 → 그 바로 옆 칸 
>wydkx → 조금 떨어진 곳

- 격자 칸 경계에 걸친 두 지점은 실제로 매우 가까워도 앞글자가 완전히 달라질 수 있습니다. 
	- 예를 들어 칸 경계를 사이에 두고 10m 떨어진 두 점이 `wydm6`과 `wydkx`처럼 공통 접두사가 짧아질 수 있습니다. 
	- 그래서 "근처 검색"을 제대로 하려면 **중심 칸 + 주변 8칸까지 함께 조회**해야 누락이 안 생깁니다.

# 2. 지도 표시

- 가장 기본 -> <mark class="hltr-yellow">타일</mark>
- 클라이언트는 사용자가 보려는 영역에 관계된 타일만 다운받아 모자이크처럼 이어 붙인 다음 화면에 뿌린다.
- 지도 확대/축소
	- 확대 수준에 따른 다른 종류의 타일을 준비

#### 경로 안내 알고리즘을 위한 도로 데이터 처리

- 대부분 다익스트라 or A* 경로 탐색 알고리즘의 변종
- 교차로를 노드(node), 도로는 노드를 잇는 선(edge)로 표현하는 그래프 자료 구로를 가정

	![[Pasted image 20260628172857.png|392]]

- 알고리즘 성능 -> 그래프 크기에 아주 민감함.
	- 전세계 도로망을 하나의 그래프로 표현 -> 메모리 Up, 성능 Down
	- <mark class="hltr-yellow">그래프를 관리 가능한 단위로 분할해야함.</mark>
	- 타일 기반 분할법과 매우 유사하게 접근(지오 해싱)

- 타일 기반 분할법과 매우 유사하게 접근(지오 해싱)
	- 그래프를 작게 나눔
	- 각각의 격자 -> 경로 안내 타일(routing tile)
	- 경로 안내 타일은 연결된 다른 타일에 대한 참조(reference)를 유지 -> 이래야지 연결된 타일들을 지나갈 때 보일 더 큰 도로망 그래프를 만들 수 있음

	![[Pasted image 20260628173257.png]]

>위의 그림의 routing tile은 특정한 지역을 포괄 -> 지도의 타일과 유사
>그러나 지도 타일=PNG(이미지), routing tile=binray file(도로 데이터)

#### 계층적 경로 안내 타일
- 경로 안내 -> 필요한 수준의 구체성을 지닌 도로 데이터가 필요함(지도!!)
	- ex) 국토 종단 여행
		- 지번 수준 정밀도 타일은 너무 많은 시간이 걸림
		- 메모리 Up, 그래프 크기 Up
- 보통 구체성 정도를 상, 중, 하로 구분
	- 상 : 가장 구체성 높음, 지방도(local roads) 데이터
	- 중 : 관할구를 잇는 간선 도로 데이터
	- 하 : 도시와 주를 연결하는 고속도로 데이터

	![[Pasted image 20260628173608.png|329]]

	- 각 타일에는 다른 정밀도 타일로 연결되는 edge가 있을 수도 있다.
		- ex) 도로 A의 특정 지점을 나타내는 노드엣 도로 F의 특정 지점을 나타내는 노드 사이에 연결선이 있어야함.

### 3. 지도 표시
- 확대 수준별로 한벌씩 지도 타일을 저장하려면 수백 PB가 필요
	- 클라이언트가 가지고 있는 것은 실용적이지 않음.
	- 확대 수준에 따라서 서버에 요청애서 가져와야한다.

#### 클라이언트는 언제 지도 타일을 서버에서 가져오는가?
>1. 사용자가 지도를 확대 또는 이동 시키면서 주변을 탐색
>2. 경로 안내가 진행되는 동안 사용자의 위치가 현재 지도 타일을 벗어나 인접한 타일로 이동한다.

#### 선택지1. 다량의 지도 타일 데이터를 효율적으로 가져오는 방법
- 현재 클라이언트가 보는 지도의 확대 수준에 근거해 필요한 지도 타일을 즉석에서 만들기.
	- 모든 지도 타일을 동적으로 만들기 -> 서버 클러스터 심각한 부하
	- 캐시 활용 어려움

#### 선택지2 .다량의 지도 타일 데이터를 효율적으로 가져오는 방법
- 확대 수준별로 미리 만들어 둔 지도 타일을 클라이언트에 전달
- 지도 타일 영역 -> 지오해싱을 통해 만든 고정된(정적인) 사각형 격자.
	- <mark class="hltr-yellow">클라이언트가 필요한 지도 타일 -> 확대 수준에 근거해서 지도 타일 집합을 만들고 -> 각 위치를 지오해시 URL로 변환</mark>
- 미리 만들어둔 정적 CDN을 통해서 서비스.
![[Pasted image 20260628180851.png]]
- 사용자에게 가장 가까운 POP(Pont Of Presence)에서 파일을 서비스
- CDN에 캐싱하기도 좋음


### 3. 데이터 사용량 줄이기

- 모바일 서비스는 데이터 사용량을 줄이는 것이 중요하다.

**경로 안내를 진행하는 동안 클라이언트가 일반적으로 필요한 데이터양을 계산해보자**
- 클라이언트 캐시 고려X -> 일반적 반복적인 중복 경로 검색을 하기 때문에 사용하면 많이 줄일 수 있음

![[Pasted image 20260705125413.png]]
> **데이터 사용량**
> - 사용자는 30km/h로 이동
> - 한 이미지가 200m x 200m(100KB)
> - 1km x 1km는 25장이 필요함 -> 2.5MB
> - 시간당 75MB 소모(분당 1.25)

> **CDN 사용량**
> - 우리는 매일 50억 minute 가량의 경로 안내처리
> - 50억 x 1.25=6.25PB/day
> - 초당 전송하는 데이터 양 62500MB
> - CDN을 사용하면 이 지도 이미지는 전 세계에 흩어져 있는 POP으로 제공
> - 200개의 POP이 았다고 하면 각 POP당 수백 MB 정도

#### 클라이언트는 CDN에서 지도 타일을 가져올 URL을 어떻게 결정할까?

- 앞선 **선택지2** 하고 가정
	- 즉 지도 타일은 이미 정의 된 격자에 맞게 확대 수준 별로 한 벌씩 미리 만들어줌.
- 지오해시 -> 모든 격자를 고유한 지오해시값
- 현재 위치 지오해시 계산 -> 클라이언트가 계산 -> CDN 요청

- 그러나 클라이언트가 구현하면 앱 지원해야할 플랫폼이 많으면 문제가 됨
	- 모바일 앱 업데이트 배포는 오래걸림

 ![[Pasted image 20260705130033.png]]

- <mark class="hltr-yellow">위 그림 처럼 주어진 위도/경도+확대수준으로 타일 URL로 변환하는 알고리즘을 따로 만들면 어떨까?</mark>
	- 유연성이 올라가기 때문에 논의해볼만한 주제임
	- a.k.a 지도 타일 서비스

1. 모바일 사용자가 타일 URL들을 가져오기 위해 지도 타일 서비스를 호출 -> 로드밸런서
2. 로드밸런서는 해당 요청을 지도 타일 서비스로 전달
3. 지도 타일 서비스는 클라이언트의 위치와 확대 수준을 입력으로 9개의 타일 URL을 계산해서 클라이언트에 반환
4. 모바일 클라이언트는 해당 타일을 CDN을 통해 다운로드

# 4. 상세 설계

우선 데이터 모델을 살펴본다. 그 다음 위치 서비스, 경로 안내 서비스, 지도 표시에 대한 상세한 설계 진행


### 1. 데이터 모델

(1) 경로 안내 타일
(2) 사용자 위치
(3) 지오코딩 데이터
(4) 미리 계산해 둔 지도 타일 데이터

#### 1. 경로 안내 타일

- 외부에서 제공받은 수많은 도로/메타데이터(이름, 관할구, 위도, 경두, 도로 부속 정보)
- 이건 그래프 자료구조로 가공되어 있진 않음(경로 안내 알고리즘 불가능)

#### 경로 안내 타일 처리 서비스

- 데이터 가공 파이프라인 -> 경로 안내 타일로 변환
- 해상도를 달리 해서 세 벌을 만듦
	- <mark class="hltr-yellow">각 타일에는 그래프의 노드와 선분으로 표현된 해당 지역 내 교차로와 도로 정보</mark>
	- 다른 타일의 도로와 연결되면 해당 정보도 있음(참조 정보)
	- 경로 안내 알고리즘은 이들 타일이 모인 결과로 만들어지는 도로망 데이터를 점진적으로 소비

#### 이런 경로 안내 타일은 어디에 저장할까?

- 방대한 양을 저장해야함
- RDB -> 비용 높고, 딱히 기능적으로 도움되지 않음
- S3 같은 객체 저장소
	- 적극적인 캐싱
	- <mark class="hltr-yellow">인접 리스트(그래프 저장)을 Binary file 형태로 직렬화 해주는 패키지가 많음</mark>
	- 타일을 지오 해시 기준으로 분류

### 2. 사용자 위치 데이터

- <mark class="hltr-yellow">엄청난 쓰기 연산 가능 / 수평적 규모 확장 가능 해야함</mark>

#### 3. 최단 경로 서비스

- 출발지와 목적지의 위도/경도를 입력해서 k개 최단 경로를 반환
- <u>처음에는 교통+도로 상황 고려 안함</u>
	- 도로 상황은 정적 -> 캐싱

- A* 경로 탐색 알고리즘의 한 형태를 실행
> 1. 입력으로 출발지와 목적지의 위도/경로를 받음. 각각 지오해싱을 해서, 경로 안내 타일을 얻음
> 2. 출발지 타일을 시작해서 그래프 자료 구조를 탐색
> 3. 탐색 볌위를 넓히는 과정에서 필요한 주변 타일은 S3에서 가져옴
> 4. 같은 지역의 다른 확대 수준 타일로도 연결가능
> 5. 고속도로만 있는 더 큰 타일로 진입할 수 있는 것은 4의 과정이 있기 떄문
> 6. 경로가 충분히 확보될 때 까지 검색 범위 확대(타일 계속 가져옴)

	- 실시간 교통 정보, 경로 안내 타일

#### 효율적인 방법

- 경로 안내를 받는 사용자의 각각의 현재 안내 타일, 그 타일을 포함하는 상위 타일(즉 , 확대 수준이 더 낮은 타일)
	- 그 상위 타일의 상위 타일을 출발지와 목적지가 모두 포함된 타일까지 재귀적으로 더해서 보관

- <mark class="hltr-yellow">O(n)으로 찾을 수 있다!</mark>

- 지속적으로 이용 가능한 경로의 ETA를 재계산해서 더 짧은 ETA 경로가 있으면 알림을 준다.
