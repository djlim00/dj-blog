# Baton | 멀티소스 데이터 수집 파이프라인 설계

> Baton은 흩어진 사내 업무 기록을 모아 검색과 AI에 활용하는 서비스입니다.
>
> 저는 데이터 소스마다 달랐던 수집 방식과 권한 모델을 통합하고, 외부 API나 Kafka에 장애가 생겨도 데이터를 잃지 않도록 수집 파이프라인을 설계했습니다.

| 구분 | 내용 |
| --- | --- |
| 담당 | 멀티소스 수집·권한 통합, Kafka 실패 처리, Outbox 설계 |
| 핵심 기술 | Spring Boot, Kafka, PostgreSQL, Outbox Pattern |

## 문제

- GitHub는 API polling, Slack은 이벤트, 파일은 직접 업로드 방식으로 들어옵니다. 소스별로 흐름을 따로 만들면 저장·이벤트 발행·모니터링 코드가 반복되고, 새 소스를 추가할 때마다 파이프라인 전체를 수정해야 했습니다.

- 외부 API 오류를 모두 같은 방식으로 재시도하는 것도 문제였습니다. 호출 제한 상태에서 요청을 반복하면 제한이 길어지고, 재시도해도 해결되지 않는 메시지는 별도 토픽에 옮겨 놓고도 운영자가 확인하거나 복구할 방법이 없었습니다.

- 문서 저장과 Kafka 발행이 하나의 트랜잭션으로 묶이지 않는 점도 문제였습니다. DB 저장 직후 Kafka가 실패하면 **문서는 있지만 후속 처리 이벤트는 없는 상태**가 될 수 있었습니다.

## 1. 수집 계약을 `discover`와 `fetch`로 통일

모든 커넥터가 두 단계의 공통 인터페이스를 구현하도록 나눴습니다.

- `discover()`: 마지막 수집 위치 이후의 새 데이터 식별
- `fetch()`: 식별한 원본과 메타데이터 수집

GitHub·Slack·파일은 수집 방식만 각자 구현하고, 정규화 이후의 저장·Kafka 발행·모니터링은 같은 흐름을 재사용합니다. 소스별 증분 수집 기준도 분리했습니다.

| 소스 | 증분 수집 기준 | 중복 방지 |
| --- | --- | --- |
| GitHub | 마지막 조회 시점과 페이지 | 원격 리소스 식별자 |
| Slack | 마지막 메시지 timestamp | 이벤트 식별자 |
| 파일 | 업로드 시점 | 파일 hash |

외부 서비스의 권한은 그대로 복사하지 않고 `추출 → 정규화 → 판정`으로 나눴습니다. 서로 다른 권한을 `PRIVATE`, `USERS`, `GROUP`, `ORG_WIDE`로 정규화해 검색 결과에서도 원본의 공개 범위를 유지하도록 했습니다.

## 2. 오류의 성격에 맞춘 Kafka Retry/DLT

오류를 HTTP 상태와 복구 가능성에 따라 분류했습니다.

- `429`: 호출 제한이 풀릴 때까지 소비를 지연
- `5xx`: `.retry` 토픽에서 일정 시간 뒤 재처리
- 반복해도 해결되지 않는 `4xx`: `.dlt` 토픽으로 격리

DLT에 메시지를 옮기는 데서 끝내지 않았습니다. 실패 메시지를 주기적으로 `dlt_archive`에 보관하고, 관리자가 원인을 수정한 뒤 관리 API로 원본 토픽에 다시 보낼 수 있게 했습니다. 자동으로 복구할 오류와 사람이 확인할 오류를 구분했습니다.

## 3. Transactional Outbox로 저장과 발행 사이의 틈 제거

문서와 발행할 이벤트를 같은 DB 트랜잭션에서 `ingest_outbox`에 저장하고, 별도의 `OutboxRelay`가 미발행 이벤트를 Kafka로 전달하도록 구성했습니다.

```text
문서 저장 + Outbox 저장 (같은 트랜잭션)
              ↓
         OutboxRelay
              ↓
            Kafka
       ↙      ↓       ↘
   텍스트 추출  검색 인덱싱  알림
```

발행에 성공하면 상태를 `PUBLISHED`로 바꾸고, 실패하면 횟수와 원인을 기록해 다시 시도합니다. 여러 인스턴스가 같은 행을 동시에 가져가지 않도록 `SKIP LOCKED`를 사용했습니다. Kafka가 일시적으로 중단돼도 발행할 이벤트는 DB에 남습니다.

## 결과

- 새 데이터 소스는 커넥터 구현만 추가하고 이후 파이프라인을 재사용할 수 있게 됐습니다.
- 일시적 실패는 자동 복구하고, 영구 실패는 조회·수정·재처리할 수 있게 됐습니다.
- 후속 소비자의 장애가 문서 수집을 막지 않으며, Kafka 장애 시에도 발행 이벤트가 유실되지 않습니다.

Outbox가 이벤트 중복까지 없애는 것은 아닙니다. Relay가 이벤트를 발행한 뒤 상태를 갱신하기 전에 중단될 수 있으므로, 소비자는 이벤트 ID를 기준으로 멱등하게 처리해야 합니다. 신뢰할 수 있는 이벤트 시스템에는 재시도뿐 아니라 중복 처리와 복구 절차도 필요하다는 점을 배웠습니다.
