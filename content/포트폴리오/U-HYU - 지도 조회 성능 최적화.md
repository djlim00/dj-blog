# U-HYU | 지오해시 캐싱과 줌 계층화를 활용한 지도 조회 최적화

> U-HYU는 U+ 멤버십 제휴 매장과 혜택을 지도에서 찾는 서비스입니다.
>
> 저는 지도 도메인과 인프라를 맡았습니다. PostGIS 쿼리를 1차로 최적화한 뒤에도 광역 조회의 큰 응답과 인기 지역의 반복 DB 조회가 남아 있어 구조를 한 번 더 개선했습니다.

| 로컬 k6 테스트 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 광역 응답 | 약 780KB | 약 22KB |
| 상세 캐시 히트 평균 | 41ms | 3.2ms |

> 운영 트래픽 수치가 아니라 동일 로컬 환경의 전후 비교입니다.

![[Pasted image 20260817214147.png|397]]

## 배경

1차 개선에서 공간 인덱스를 활용하도록 `ST_DWithin` 쿼리를 수정하고, 1:N JOIN의 카디널리티 증가와 엔티티 재조회 문제를 제거해 서울역 20km 조회 평균을 301ms에서 41ms로 줄였습니다.

하지만 20km 반경을 조회하면 약 2,000~3,000개의 매장을 반환했고, 프론트는 이를 30~50개의 마커로 다시 묶었습니다. 화면에 쓰이지 않을 상세 데이터까지 전송한 셈입니다. 강남·판교처럼 요청이 몰리는 지역에서는 좌표가 몇십 미터만 달라도 거의 같은 결과를 PostGIS가 매번 다시 계산했습니다.

![[Pasted image 20260817202357.png]]

## 1. 지오해시 셀 단위 캐싱

위경도 요청값 전체를 키로 사용하면 지도를 조금만 움직여도 캐시를 재사용할 수 없습니다. 공간을 일정한 셀로 나누는 지오해시를 캐시 키로 선택한 이유입니다.

- 상세 뷰포트에 맞춰 precision 6(위도 37도 기준 약 1.2km × 0.61km)을 선택
- 뷰포트와 겹치는 셀을 계산한 뒤 Redis `MGET`으로 일괄 조회
- miss가 난 셀만 DB에서 가져와 write-back
- 셀 경계에서 중복된 매장은 ID로 제거하고 정확한 반경 조건을 마지막에 적용
- 필터 조합별 키를 만들지 않고 원본 셀을 저장한 뒤 애플리케이션에서 필터링

```text
뷰포트 → 겹치는 지오해시 셀 계산 → Redis MGET
                                  ├─ hit → 결과 병합
                                  └─ miss → PostGIS → write-back
```

여러 요청이 동시에 같은 hot cell을 채우는 cache stampede는 `SETNX` 기반 single-flight lock으로 완화했습니다. Redis 장애가 지도 서비스 전체로 번지지 않도록 Resilience4j Circuit Breaker가 DB 조회로 폴백합니다.

매장 변경 시에는 `@TransactionalEventListener(AFTER_COMMIT)`에서 관련 셀을 무효화합니다. 커밋 전에 캐시를 지웠다가 롤백되는 정합성 문제를 피하고, TTL 24시간은 이벤트 누락에 대비한 안전장치로 뒀습니다.

## 2. 줌 레벨별 데이터 계층화

광역 지도에서는 개별 매장의 상세 좌표보다 전체 분포가 중요합니다. 카카오맵 줌 레벨을 세 계층으로 나누고, 각 계층에서 반환하는 데이터의 해상도를 달리했습니다.

| 계층 | 화면 범위 | 반환 데이터 | 지오해시 precision |
| --- | --- | --- | --- |
| L1 광역 | 10km 이상 | 셀·브랜드별 개수와 대표 좌표 | 4 |
| L2 지역 | 1~10km | 브랜드별 대표 매장 | 5 |
| L3 상세 | 1km 이하 | 개별 매장 | 6 |

L1·L2 집계는 `store_geo_agg`에 미리 계산합니다. 매일 배치로 전체를 보정하고, 매장 CRUD 이벤트가 발생하면 해당 셀만 부분 갱신합니다. L3는 앞서 만든 셀 캐시를 사용합니다.

## 트레이드오프와 다음 검증

캐시 miss는 Redis write 비용이 추가돼 기존 DB 조회보다 조금 느릴 수 있습니다. 집계 데이터도 원본과 짧은 시간 차이가 생길 수 있습니다. 현재 결과는 로컬 데이터와 부하 시나리오에서 얻은 값이며, 실제 운영 트래픽의 분포를 뜻하지는 않습니다.

배포 전에는 운영과 비슷한 데이터로 p95·p99, hit ratio, DB QPS를 다시 측정할 계획입니다. Redis 장애 폴백과 매장 이동 시 이전·새 셀 무효화도 통합 테스트 대상입니다. 성능 수치만 제시하기보다 어떤 조건에서 얻었는지 재현 가능하게 남기고자 했습니다.
