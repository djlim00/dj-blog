# 백엔드 개발자 임동준 포트폴리오

> 서비스를 개발할 때 성능과 안정성을 함께 고민합니다. 문제가 생기면 먼저 수치로 확인하고, 원인을 찾은 뒤 구조를 개선해 왔습니다.
>
> 성능 최적화부터 비동기 파이프라인, 고가용성, 모니터링까지 직접 다뤘습니다. 어떤 기술을 썼는지보다 그 기술이 왜 필요했고, 사용자 경험을 어떻게 바꿨는지를 더 중요하게 생각합니다.

## 기술

**Backend** `Java` `Spring Boot`  
**Data** `PostgreSQL` `PostGIS` `Redis` `Kafka`  
**Infra & Monitoring** `Docker` `AWS` `Prometheus` `Grafana`

## 1. U-HYU | 지도 조회 성능 최적화

> **문제**
>
> 20km 반경을 조회하면 약 2,400개의 매장이 한꺼번에 반환됐습니다. 응답 크기는 780KB까지 늘어났고, 인기 지역에서 비슷한 요청이 반복될 때마다 DB가 같은 결과를 다시 계산했습니다.

**개선**  
지도 줌에 맞춰 집계·대표·상세 데이터로 응답을 나눴습니다. 넓은 지역에서는 매장 분포만 보여주고, 상세 조회에는 지오해시 셀 단위 Redis 캐시를 적용했습니다.

### 결과

- 광역 응답 크기 `780KB → 22KB` — 약 97% 감소
- 상세 캐시 히트 평균 `41ms → 3.2ms`
- Redis 장애 시 Circuit Breaker를 통해 DB로 폴백

**기술** `Spring Boot` `PostGIS` `Redis` `Geohash` `k6`

## 2. StudyGroup | Redis 세션 고가용성

> **문제**
>
> Redis를 재기동하는 동안 인증 API가 실패했고, 저장된 세션도 사라져 모든 사용자가 다시 로그인해야 했습니다. Redis 한 대의 문제가 곧 서비스 장애로 이어지는 구조였습니다.

**개선**  
Redis Sentinel로 데이터를 복제하고, HAProxy가 현재 Master를 찾아 연결하도록 구성했습니다. 배포처럼 종료 시점을 아는 경우에는 Master를 먼저 전환한 다음 기존 노드를 내리도록 순서를 바꿨습니다.

### 결과

- 단일 Redis 장애점 제거 및 세션 유지
- 강제 종료 시 실패 구간 `8~15초 → 약 6초`
- 계획된 재기동에서 100ms 측정 간격 기준 요청 실패 미관측

**기술** `Spring Session` `Redis Sentinel` `HAProxy` `Docker`  
**상세** [[StudyGroup - Redis 세션 고가용성 개선|구현과 검증 자세히 보기]]

## 3. Baton | 멀티소스 데이터 수집 파이프라인

> **문제**
>
> GitHub·Slack·파일은 수집 방식도, 권한 체계도 서로 달랐습니다. 소스마다 처리 흐름을 따로 만들면 같은 코드가 반복됐고, 외부 API나 Kafka에 장애가 생겼을 때 데이터가 유실되거나 실패 메시지가 그대로 방치될 수 있었습니다.

**개선**  
수집 과정을 공통 인터페이스로 묶고 권한 모델을 통일했습니다. 오류의 성격에 따라 Retry와 DLT로 처리 흐름을 나눴으며, DB 저장과 Kafka 발행 사이에는 Transactional Outbox를 적용했습니다.

### 결과

- 새 데이터 소스 추가 시 기존 저장·처리 파이프라인 재사용
- 일시적 실패는 자동 재시도, 영구 실패는 보관 후 관리자 재처리
- DB 저장과 Kafka 발행 사이의 이벤트 유실 방지

**기술** `Spring Boot` `Kafka` `PostgreSQL` `Outbox Pattern`  
**상세** [[Baton - 멀티소스 데이터 수집 파이프라인|구현과 검증 자세히 보기]]

## 4. Uplait | AI 챗봇 관측 가능성

> **문제**
>
> 챗봇 응답이 느리거나 실패해도 Spring, FastAPI, OpenAI API, pgvector 중 어느 구간에서 문제가 생겼는지 로그만으로는 바로 알기 어려웠습니다.

**개선**  
각 호출 구간의 지연·실패·재시도를 지표로 나눴습니다. 알림 발생부터 해소까지 이력과 Ack를 관리하는 콘솔을 설계하고, Prometheus의 단일 장애점을 보완하기 위해 Thanos 구성도 POC했습니다.

### 결과

- 챗봇 장애를 요청 구간별 지표로 분리할 수 있는 관측 기준 수립
- 알림 발생·반복·해소·담당자 확인 이력을 남기는 운영 흐름 설계
- Prometheus 단일 장애점과 장기 저장 문제의 개선안 검증

**기술** `Prometheus` `Grafana` `Alertmanager` `Micrometer` `Thanos`  
**상세** [[Uplait - AI 챗봇 관측 가능성 설계|설계와 POC 자세히 보기]]

## 개발 원칙

- 평균 응답 시간 하나만 보지 않습니다. p95와 실패율, 페이로드처럼 사용자가 실제로 겪는 문제와 가까운 지표를 확인합니다.
- 장애 대응도 자동 재시도에서 끝내지 않고 기록과 확인, 재처리 경로까지 함께 설계합니다.
- 현재 트래픽과 팀이 감당할 수 있는 범위 안에서 필요한 만큼 복잡도를 더하는 것이 제 개발 원칙입니다.

> U-HYU의 성능 수치와 StudyGroup의 장애 시간은 동일한 로컬 테스트 환경에서 측정한 전후 비교입니다.
